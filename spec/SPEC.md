| **This revision (v2.2)** | Closes the arbiter freeze loophole in multi-commit decomposition (§13.6.5; new FR-M1d, amended FR-M9/M10). In v2.0–v2.1 the arbiter's _gate_ (`git status --porcelain`) and _resolution staging_ (`git add -A` / `git add`) read the **live** working tree while its _diff_ input was the frozen `T_start` — so a change added to the working tree after the start-of-run freeze (e.g. an editor save during the planner call) was silently swept into an arbiter commit, contradicting FR-M1b. **FR-M1d** extends the freeze boundary into the arbiter: gate, diff, and staging all derive from `T_start`; concurrent changes are left untouched in the working tree. Adds one git primitive (`OverlayTreePaths`, §13.6.5). No commit/rescue/CAS/lock logic changes; no config or CLI surface changes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **This revision (v2.3)** | Adds the **multi-turn generation fallback** (§9.24; new FR-T1–T12, → G21): when a one-shot generation of a large diff fails (provider per-request unreliability that can fall well below the advertised context window), losslessly re-deliver the full diff across request-sized provider session turns so a single commit message can still be produced — without truncation and without decomposing into multiple commits. Adds a `session_mode` manifest field (§12.1; pi = `"append"`, verified) and two config knobs (`multi_turn_fallback`, `multi_turn_chunk_tokens`). Withdraws the `FUTURE_SPEC.md` rejection of large-diff chunking for the lossless form (the lossy map-reduce form stays rejected). Scope: message role only (planner/stager/arbiter out of scope this revision). No commit/rescue/CAS/lock changes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **This revision (v2.4)** | Adds **hook execution on the commit path** (§9.25; new FR-V1–V8, → G22): the plumbing path (`commit-tree` + `update-ref`) no longer bypasses the repository's git hooks. The full commit hook sequence — `pre-commit` → `prepare-commit-msg` → `commit-msg`, then `post-commit` after publication — runs around each commit, faithfully emulating `git commit`'s hook ordering without abandoning the snapshot/CAS atomic-commit core (§8). A new `--no-verify` flag (env `stagecoach_NO_VERIFY`, git config `stagecoach.no_verify`; default off) skips `pre-commit` and `commit-msg` ONLY, mirroring `git commit --no-verify` exactly (`prepare-commit-msg` and `post-commit` still run). Closes the long-standing §5 caveat that the plumbing path bypassed hooks (FR-H7/US19 reframed): hook mode (§9.20) remains as the bridge for plain `git commit` from IDEs, and is no longer the _only_ way to get hooks. No commit/CAS/rescue/lock regression: a hook abort is an existing-path rescue (no `update-ref` ran).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **This revision (v2.5)** | Two reliability-hardening fixes surfaced by a large-diff failure investigation. **(1) Closed-loop token-budget guarantee (§9.1; new FR3j, amended FR3d).** The `token_limit` water-fill (FR3i) sized diff bodies by subtracting _estimates_ of the non-body parts from `token_limit` — an open-loop budget whose estimation drift let the _assembled_ prompt land slightly over the limit (observed ~152K tokens delivered against a 150K `token_limit`, before the model's own sub-window unreliability even came into play). FR3j adds a closed-loop backstop: after the water-fill, stagecoach assembles the _actual_ full prompt, measures it with the same `chars/4` estimator, and re-trims until it fits, making "the prompt never exceeds `token_limit`" a hard invariant (going under is always fine); FR3i is reframed as the first-cut allocator under that guarantee. **(2) Stale lock-file reaping (§18.5; amended FR52).** `flock` auto-releases on process death, so the _lock_ never goes stale — but the lock _file_ survived any non-deferred exit (the signal-rescue path's `os.Exit`, `SIGKILL`, a crash) and accumulated as unbounded disk litter. §18.5 corrects its "no stale locks to reap" over-claim: a lock file is stale iff its recorded `pid` is a dead process on its `hostname`; stagecoach reaps such files on acquire (self-healing, never a live pid), and the signal-rescue path now releases the file before exiting (reaping stays as the backstop for `SIGKILL`/crash). No commit/CAS/rescue behavior changes. |
| **This revision (v2.6)** | Adds **work-description mode** (§9.26; new FR-W1–W8, → G23): an opt-in, description-first commit mode for workflows that already have a task/work description before implementation (e.g. a task system that calls stagecoach after each unit completes). Instead of feeding the whole diff and making the model reverse-engineer intent, stagecoach leads with the user-supplied `--work-description` + the numstat skeleton (filenames), and the model pulls specific file diffs on demand via a **loose `READ <path>` text protocol** — not tool-calling, so it needs no tool-calling support and runs in bare mode on every provider. The read loop accumulates in one provider session via `session_mode = "append"` (reusing the §9.24 multi-turn machinery — no new provider dependency), with chunked reads behind an implicit cursor (re-requesting a path returns the next chunk; the model manages no tokens) and a bounded, configurable round cap (default 5) that forces a commit message after N read rounds. Message role only; never the default (its value is contingent on a rich description). Adds one config knob (`work_desc_read_rounds`). No commit/CAS/rescue/lock changes. |
| **This revision (v2.7)** | Adds **orphaned-run lock reclamation** (§9.27; new FR-K1–K7, → G24; amended §18.4/§18.5, FR52): a third lock state the §18.5 model did not contemplate. `flock` auto-releases on process death and a live `pid` is never reaped — correct for a _killed_ holder and a _legitimate_ live run, but not for a holder whose **launcher closed without killing it** (closing the lazygit TUI (§9.21), quitting an IDE, a detaching terminal). That child is **reparented to init and keeps running**: its `pid` stays alive (so pid-liveness reaping never fires) and §18.4's `SIGINT`/`SIGTERM`-only handler receives neither signal, so the run never reaches the exit path and the lock file outlives the launcher until the orphan's generation finishes — or indefinitely if its provider subprocess is wedged by the vanished terminal. This is the "the lock stays forever" report. The fix is **self-termination, never contender-side force-breaking**: on startup stagecoach records its parent pid and a watchdog routes the process through the _existing_ rescue + lock-release exit path when the parent dies (FR-K1; abandoning an in-flight commit is always safe — HEAD moves only at `update-ref` (§13.2), the snapshot is a gc'able orphan whose SHA the rescue recipe prints). Detection is by **parent-pid change** (reparenting), not the brittle `getppid()==1` test (FR-K2); `SIGHUP` joins the caught signals so a terminal hangup routes through rescue instead of a raw terminate (FR-K3); `stagecoach lock status` prints the holder's path/liveness/orphan-status read-only so a blocked user can `kill`/`rm` themselves (FR-K4); the Busy message puts the lock path on its own line and flags an orphaned holder (FR-K5); an opt-out (`stagecoach.no_parent_watchdog` / `stagecoach_NO_PARENT_WATCHDOG`) covers intentional detachment (`nohup`/`setsid`/`systemd-run`) (FR-K6); the watchdog is Unix-only — on Windows `flock` is already a no-op and the CAS is the guarantee (FR-K7). FR52's "never force-break" guarantee is preserved unchanged: the watchdog is the _same_ process abandoning its own unwanted work, never a contender breaking another's live lock. No commit/CAS/rescue/index behavior changes. |
| **This revision (v2.8)** | Adds **per-role generation timeouts** (§9.15 new FR-R7; amended FR25/FR-T5/§16.1–§16.4): each role (planner, stager, message, arbiter) resolves its OWN timeout — there is no single shared budget. The global `--timeout` / `STAGECOACH_TIMEOUT` / `stagecoach.timeout` / `[defaults].timeout` (default `120s`) is the fallback a role inherits; per-role overrides are `--<role>-timeout` / `STAGECOACH_<ROLE>_TIMEOUT` / `[role.<role>].timeout` / `stagecoach.role.<role>.timeout`, mirroring provider/model/reasoning. **Built-in role default: planner `480s`** — it is the heavy role (reasoning over the entire frozen `T_start` diff before emitting its JSON partition routinely exceeds the lighter roles' budget); stager/message/arbiter inherit `120s`, each independently tunable. Motivated by a real `decompose: planner failed: context deadline exceeded` with a thinking-high planner over a large diff. Also hardens the decomposition freeze (§9.14 new FR-M1e; amended FR-M1c): the decompose entrypoint re-asserts FR-M1's empty-index precondition and refuses with a clear, actionable error if the index is non-empty (defense-in-depth — the trigger is the primary guard, but a stale/buggy trigger now fails loudly with a remedy instead of the opaque `freeze violation: … not traceable to T_start`), and FR-M1c's hard error now names the offending paths and remedy. No commit/CAS/rescue/lock changes. |
| **This revision (v2.9)** | Adds **chrome-disable for every provider** (§9.28; new FR-C1–C5, → G25; extended §12.7.1). §12.7.1's tools-disable asymmetry guarantees **mutation** safety (the read-only constraint) but is silent on **agent chrome** — skills, extensions/prompt-templates, context files, and MCP servers — which a provider may still discover, load, spawn, and inject into the prompt on a one-shot commit-message call (startup latency, token/quota waste, nondeterminism, MCP-server failure modes). FR-C1–C5 require every built-in provider to render **chrome-less** for every surface the agent CLI exposes a disable switch for (pi already sets the bar; claude via `--tools ""`/`--setting-sources ""`), to set any real MCP-disable flag explicitly (pi today has NO `--no-mcp` — only `--mcp-config <path>` — so MCP tool *use* is only indirectly suppressed by `--no-tools`), and — for the read-only-constrained providers (codex/cursor/opencode/agy/qwen-code) that offer no per-surface switches — to disable what they DO expose and document the rest as a tracked limitation rather than hide it. Verification discipline mirrors FR-D5/FR-T9 (per-`--help`, dated, recorded in each manifest header's CHROME-DISABLE note). No commit/CAS/rescue/lock changes; mutation safety unchanged (the read-only constraint stays). |
| **This revision (v3.0)** | Adds **self-update** (§9.29; new FR-U1–U12, → G26) and **expands the distribution surface** (§21; npm wrapper, Winget, Nix flake, mise/asdf plugins → G27). v3.0 **supersedes the v2.1 rejection of self-update** (Appendix F): the prior rejection assumed self-update meant a tool that downloads and overwrites its own binary, which fights whatever package manager installed it and gets silently reverted on that manager's next upgrade. The resolution is the inverse architecture — **install-method-aware, delegate-first**: `stagecoach upgrade` detects how the binary was installed and delegates to that channel's native updater wherever one exists (Homebrew/Scoop/Winget/npm/mise/asdf/go-install), prints the command where running it needs privileges (AUR) or is declarative (Nix), and falls back to a verified, atomic, rollback-able direct-binary swap ONLY for the direct-binary (curl\|sh / manual-download) channel. A single memorable command across every channel that never fights a package manager, because it never overwrites a package-manager-owned file. The command is walled off from the commit-generation core: it acquires no run lock, reads no repository, invokes no provider, and never touches any index or ref — §19's "stagecoach makes no network calls itself" is scoped to the commit path, and this section is its explicit, named exception (the call fetches only the project's own release artifacts and checksums; never credentials, never a diff, never repo data). Also adds `--check` (update-available probe for CI/cron, exit 6), `--rollback` (one-step restore of the prior binary), mandatory SHA256 checksum verification, and a new-binary sanity run before swap. No commit/CAS/rescue/lock changes; the new channels (npm wrapper, Winget, Nix flake, mise/asdf) are build/release plumbing documented in §21 with no FR surface. |
| **This revision (v3.1)** | Adds **native Linux package formats** — `.deb` (Debian/Ubuntu/Mint) and `.rpm` (Fedora/RHEL/Rocky/Alma/openSUSE) — to the release surface (§21.2/§21.3; new G28; amended §9.29 FR-U2/FR-U3). Produced by goreleaser's native `nfpms:` pipe (no external repo, no CI step): every GitHub Release ships `stagecoach_<v>_linux_amd64.{deb,rpm}` + `_arm64.{deb,rpm}` alongside the existing archives, installing to `/usr/bin`. This is the distribution convention for the tool's target ecosystem (lazygit, ripgrep, bat, fd, gh all ship `.deb`/`.rpm` in releases). Because these are GitHub-Release assets with NO apt/dnf **repo**, the package managers' own updaters cannot fetch a new version — so `stagecoach upgrade` detects a `.deb`/`.rpm` install (FR-U2: `dpkg -s stagecoach` / `rpm -q stagecoach` join the tier-(b) query table as the `deb`/`rpm` channels) and, per FR-U1, refuses to self-swap the package-manager-owned `/usr/bin/stagecoach`; instead FR-U3 PRINTs the manual update recipe (download the new package from Releases + `sudo apt install --only-upgrade stagecoach` / `sudo dnf upgrade stagecoach`, with the no-repo fallback noted) and exits 0, mirroring the AUR/Nix print-don't-run rows. No commit/CAS/rescue/lock changes; no commit-path FR surface. |
| **This revision (v3.2)** | Adds the **file-disjoint staging fast-path** to multi-commit decomposition (§9.14 new FR-M13/FR-M14, → G29; amended §13.6.3). The stager is the pipeline's only **tooled** agent and its only inherently serial step — every stager mutates the same live index, so staging cannot parallelize and message generation is capped at the 1-deep overlap of FR-M6. But the planner already emits a **file-level** partition (`files` per concept), and the stager exists solely to **hunk-split** a file shared across concepts. When the partition is **pairwise file-disjoint** (no path in two concepts' `files`) — the common case for cleanly separated changes — stagecoach stages each concept **deterministically** with `git add` (adds, modifications, and deletions for those whole paths) under the unchanged accumulate-never-reset index model, **invoking no stager agent at all**: whole-file staging realizes the planner's declared partition exactly, because a path claimed by one concept cannot need a hunk split. With all `tree[i]` frozen before any message starts, the N message generations then run **concurrently** and publish in CAS order, collapsing a disjoint run's critical path from "planner + ~N sequential steps" to "planner + one message latency." FR-M1c (`verifyFreezeSubset`) runs unchanged on every fast-path tree (whole-path adds of `T_start` content pass trivially), so the freeze-boundary guarantee is identical to the tooled path; unclaimed paths still flow to the arbiter (FR-M9). A partition with any shared file falls back transparently to the FR-M5 tooled stager for the whole run — the fast-path is automatic, deterministic, and adds no configuration. Side effect: a provider whose manifest declares no `tooled_flags` (FR-D4 — opencode, qwen-code) can now decompose a disjoint tree, where it otherwise could not serve the stager role. No commit/CAS/rescue/lock/arbiter behavior changes; the §13.6.3 tree-to-tree-diff and serialized-CAS invariants are preserved. |

## 0. How to read this document

This is two documents fused into one:

- **Part I — Product Requirements (PRD):** sections 1–10. What we are building, for whom, why it is different, and what is explicitly out of scope. Read this to understand the _why_ and the _what_.
- **Part II — Technical Specification:** sections 11–22. How it is built: package layout, provider manifest schema, git internals, CLI reference, config model, testing, release. Read this to implement it.

Appendices (A–F) contain reference material: full prompt templates, example terminal sessions, and a line-by-line porting map from `commit-pi`.

Ideas that are deferred or deliberately rejected live in **`spec/FUTURE_SPEC.md`** (alongside this spec, deliberately not linked into it), each with its rationale. This document intentionally contains no stubs or placeholders for unbuilt features — if a capability is described here, it is in scope.

The single most important section for understanding the product's defensibility is **§5 (Unique Value Proposition)** and the single most important section for understanding the engineering is **§13 (The snapshot-based generation flow)**. If you read only two sections, read those. The most important section for understanding the **multi-commit** feature — the v2.0 headline addition — is **§13.6 (Multi-commit decomposition)**; read it alongside §13.1–§13.5, which it composes.
